01 Overview

I built a tool to do the QA nobody had time for.

I was the only designer across five legal-tech products at Omnis AI. Before each release I checked every screen by hand, and it took hours. So I built a tool that does the checking, and I keep the final say.

02 The problem

Most design bugs show up only after a click.

A screen can pass review when it first loads. The problems show up after someone opens a dropdown, submits a form with an error, or lands on an empty page. Nobody had time to click through all of those states before each release, so those bugs reached real users.

The goalCheck every state of every screen, fast enough to run before each release, and accurate enough that engineers would trust it.

03 Solution

Three parts: a clicker, a checker and a reporter.

PartWhat it doesWhat you get
CrawlerLogs in and clicks through screens, menus, dialogs and tabsA record of each state it reached
CheckerRuns 229 fixed rules (contrast, tokens, accessibility), then an AI pass for layoutProblems, each tied to a real element
ReporterSorts problems into a view for each roleA report with the exact code fix per problem

Built for product designers, frontend engineers, QA, content designers and the managers who sign off on releases.

04 Background

One designer, five products, no QA team.

A typical manual check meant taking screenshots, drawing red boxes in Figma, listing the design tokens and writing tickets. When engineers fixed something, I checked everything again. Design QA became the thing holding releases back.

05 Design process

Version one invented a button. Version two checks the real page.

Each version tested one question: can a tool find design problems engineers trust enough to fix?

V1 · Rejected

Reading screenshots with AI

A vision model listed problems from screenshots. On a dashboard I knew well it reported low contrast on “the secondary button beside the search field.” That button didn’t exist.

Final

Checking the real page, with proof

The tool works inside a live browser, runs 229 fixed rules first and uses AI only for layout. Any problem that can’t point to a real element is thrown out.

InsightIf one finding is made up, you double-check all of them. So the tool drops any finding it can’t tie to an element.

07 Design decisions

Proof first, clicks before judging, fixes ready to paste.

01

Proof before opinion

Fixed rules handle what can be measured: contrast, accessibility attributes and design tokens. AI handles judgement calls, only when it can point to the element.

02

Click before judging

The tool opens each dialog, dropdown, drawer and tab before it reviews a screen.

03

Every problem comes with its fix

Each card shows severity, the rule, a plain title, the principle behind it, a copy-paste CSS fix and a confidence score.

04

Each role sees its own list

One run, six readers: designer, frontend, QA, content, engineering manager and leadership.

09 Looking back

What building it taught me.

01

Trust comes before speed

A tool that reports 50 problems with 15 made up costs more time than checking by hand.

02

Real checks need clicks

Looking only at first loads misses overflowing dropdowns, error messages and empty pages.

03

Engineers fix what they can paste

A selector and a code fix get merged. A vague comment gets skipped.

Next If I pick it back up

  • Remember a baseline per product so runs flag only new problems.
  • Run on every staging deploy through GitHub Actions.
  • Re-check after a fix is merged.
  • Send verified notes back into Figma.
10 Questions I expect

Questions I expect

Are you a designer or an engineer?

Product design is my foundation: research, UX architecture, interaction design and design systems. I also write production TypeScript to ship working prototypes and tooling end to end.

How do you prevent hallucinations?

Deterministic checks cover objective rules like contrast maths and ARIA. AI findings are rejected unless they map to a real DOM node.

How is this different from axe-core or Lighthouse?

Those check one static URL. This engine signs in, crawls interactive states, pairs axe-core with layout checks and exports ready-to-paste fixes.

Can it run in CI?

Not yet. Running on every staging deploy and flagging blockers on pull requests is the next step.
